# Ticket clustering

Изолированный экспериментальный контур поиска тематических подкластеров в обращениях ТП.

Контур читает `ticket_analytics.sqlite3` в режиме SQLite `mode=ro`. Он не изменяет CSV, Qdrant,
основную аналитическую базу или production RAG. Все кэши и отчёты записываются только в локальные
`ticket_clustering/artifacts/` и `ticket_clustering/reports/`.

## Baseline без Optuna

Первая версия выполняет:

1. фильтрацию по исходной категории обращения;
2. загрузку только `ticket_symptoms` — названия и решения не используются;
3. детерминированную нормализацию и оценку информативности без агрессивного исключения;
4. embeddings уникальных симптомов;
5. точный блочный cosine kNN;
6. mutual-kNN граф с порогом similarity;
7. Louvain communities с фиксированным seed;
8. локальный HTML и сырой JSON для аудита качества.

## Стратегии графа

- `semantic-only` — исходная cosine similarity без предметных поправок;
- `semantic+entities` — similarity с учётом явно найденных серий, модулей, протоколов,
  библиотек и программных компонентов.

В `semantic+entities` совпадение одной только серии оборудования не увеличивает similarity:
`R500` — слишком широкая тема. Точная несовместимость одиночных серий блокирует ребро
(`R500` и `R500S` считаются разными), а совпадение протокола, модуля или компонента усиливает его.
Общие типы событий сохраняются в отчёте для диагностики, но не дают бонуса при кластеризации.

## Пригодность для статьи

Каждый кластер получает отдельную детерминированную оценку `article_readiness`:

- `ready` — достаточно связный и предметный кандидат для одной статьи;
- `review` — возможный кандидат, который стоит проверить или дополнительно разделить;
- `not_ready` — слабый, слишком общий либо слишком маленький кластер.

Оценка не использует решения тикетов и ничего не удаляет. Её признаки и причины сохраняются
в JSON, а HTML сортирует готовые кандидаты первыми. Пороговые значения находятся в секции
`article_readiness` файла `baseline_config.yaml`.

Крупные кластеры со статусом `review` автоматически проходят второй, более строгий этап
кластеризации. Разбиение принимается только при наличии нескольких устойчивых подкластеров и
достаточном покрытии родительских симптомов. Родитель сохраняется для аудита. Готовые первичные
кластеры и готовые подкластеры объединяются в массив `article_candidates` сырого JSON; каждый
кандидат содержит полный список `ticket_ids` для последующего присоединения решений.

Запуск для категории из `baseline_config.yaml`:

```powershell
& C:\Users\e.valov\AppData\Local\anaconda3\envs\rag_langchain\python.exe -m ticket_clustering.run_baseline
```

Явное A/B-сравнение стратегий:

```powershell
& C:\Users\e.valov\AppData\Local\anaconda3\envs\rag_langchain\python.exe -m ticket_clustering.run_baseline --strategy semantic-only
& C:\Users\e.valov\AppData\Local\anaconda3\envs\rag_langchain\python.exe -m ticket_clustering.run_baseline --strategy semantic+entities
```

Проверка входа без модели и записи файлов:

```powershell
& C:\Users\e.valov\AppData\Local\anaconda3\envs\rag_langchain\python.exe -m ticket_clustering.run_baseline --dry-run
```

Повторная генерация существующего отчёта требует явного `--replace`. Кэши embeddings и kNN
версионируются fingerprint-ом модели и входных симптомов; совпадающий валидный кэш используется повторно.

Optuna в baseline не используется. Она будет добавлена отдельным этапом после оценки качества и
определения метрик, которые действительно соответствуют пригодности кластера для одной статьи.

Сравнить все уже построенные baseline-отчёты в одной HTML-странице:

```powershell
& C:\Users\e.valov\AppData\Local\anaconda3\envs\rag_langchain\python.exe -m ticket_clustering.compare_baselines --replace
```

Покрытие и similarity в таблице — диагностические показатели, а не автоматическая оценка качества.
Смысловую однородность нужно проверять по раскрывающимся примерам кластеров. Позже эта ручная
проверка станет основанием для целевой функции Optuna.
