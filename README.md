# RegLab RAG для документации и тикетов

Проект собирает RAG-систему для технической поддержки: поиск по документации, поиск по историческим обращениям, генерация приватного ответа ИИ для специалиста ТП и вспомогательные пайплайны обработки данных.

Текущий фокус системы - сценарий "приватный ответ после создания заявки": сначала находится полезная информация в документации, затем отдельно подбираются похожие тикеты с кратким описанием проблемы и решения. `equipment_filter` в основном поиске не используется, потому что документация часто пересекается между типами оборудования. HyDE в основном production-пути также не включается.

## Основные части

- `src/` - ядро приложения: конфигурация, RAGEngine, логирование, обработка документов и retriever-ы.
- `scripts/` - CLI, API-сервер, ingestion, экспорт тикетов, автотесты и утилиты запуска.
- `src/document_processing/` - парсинг DOCX/HTML/JSON, очистка тикетов, подготовка parent/child-документов.
- `src/retrieval/` - Qdrant retriever-ы, раздельный поиск по документации и тикетам, rerank.
- `src/module_detection.py` - детерминированное определение модулей ПЛК по алиасам, расширение поискового запроса и ранжирование тикетов по найденным модулям.
- `src/context_formatting.py` - форматирование найденных документов/тикетов для LLM, стабильные ID источников `[D1]`/`[T1]`.
- `src/evidence_guard.py` - защитные правила против неподтвержденных расшифровок и выводов по косвенным совпадениям.
- `src/utils/` - диагностика баз, моделей, структуры проекта и профилирование.
- `data/`, `vector_dbs/`, `reports/`, `benchmark_results/`, `result_test_auto/` - рабочие данные и результаты запусков.

## Production-поток

1. Документация и тикеты превращаются в документы LangChain.
2. Child-чанки индексируются в Qdrant, parent-документы хранятся отдельно.
3. `DualRetriever` выполняет отдельный поиск по документации и по тикетам.
4. Перед LLM выполняется детерминированное обогащение запроса: поиск модулей по алиасам, точный добор документации по модульным разделам и добор тикетов по `mentioned_module_codes`.
5. Контекст получает стабильные source-id прямо в заголовках фрагментов, чтобы LLM ссылалась на конкретный найденный блок, а не только на общий список источников.
6. `RAGEngine.process_support_ticket()` собирает приватный ответ: сводка, данные из документации, похожие обращения, риски и вопросы для уточнения.
7. `evidence_guard` применяет пост-проверки для запросов на расшифровку обозначений: если прямого определения в контексте нет, гипотезы о значении суффиксов не выдаются.
8. `scripts/api_server.py` отдает HTTP API для интеграции с порталом поддержки.

## Настройка

Основные параметры лежат в `config.yaml`, секреты и API-ключи - в `.env`. Для Qdrant используется `docker-compose.yml`. Перед запуском ingestion или API проверь, что коллекции и пути к parent-store в конфиге соответствуют текущей базе.
Структурированный planner поисковых запросов включается отдельно через `retrieval.multi_query.structured_planner.enabled`. При `false` сохраняется прежний общий список multi-query; при `true` planner формирует разные запросы для официальной документации и исторических тикетов. Лимиты задаются параметрами `max_documentation_queries` и `max_ticket_queries`. Экспериментальный `query_aware_rerank.enabled` повторно оценивает RRF-кандидата по исходному вопросу и лучшему сгенерированному запросу, сохраняя ограниченные фасетные квоты; режим выключен по умолчанию из-за дополнительной нагрузки на CrossEncoder.

Agentic RAG публикуется API-сервером как модель `reglab-ai-agentic`, если `agentic_rag.enabled: true`. Модель переиспользует загруженный `deep`-движок, но добавляет ограниченный цикл проверки достаточности доказательств и уточняющих поисков; старые сообщения чата не передаются в движок.

## Типовые команды

```bash
python scripts/run_ingest_qdrant.py
python scripts/api_server.py
streamlit run scripts/app_streamlit.py
python scripts/test_tickets_search.py
```

Команды зависят от локального окружения, Qdrant и настроенных ключей LLM.
